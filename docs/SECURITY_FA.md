# امنیت و نگهداری داده

## کنترل‌های پیاده‌سازی‌شده

- رمز مدیریتی با Argon2 ذخیره می‌شود؛ حداقل طول ۱۴ نویسه است.
- نشست، cookie تصادفی و opaque دارد؛ digest نشست، نسخهٔ دسترسی، CSRF و زمان انقضا در دیتابیس نگهداری می‌شود. تغییر رمز یا غیرفعال‌سازی کاربر نسخهٔ نشست را عوض می‌کند.
- فرم‌های تغییر وضعیت، تخصیص، پاسخ، دعوت و تغییر حساب CSRF token دارند. ورود و عضویت تیم از double-submit امضاشده با HMAC و SameSite=Lax استفاده می‌کنند.
- تلاش ورود برای هر IP در دیتابیس محدود می‌شود. در تولید HTTPS و Trusted Host فعال است؛ API و Uvicorn فقط به loopback متصل‌اند.
- پنل security headers، CSP، منع frame، `nosniff`، Referrer Policy و HSTS دارد. CSS/JS داخلی‌اند و CSP به inline script یا style نیاز ندارد.
- هر route مدیریتی نقش را سمت‌سرور بررسی می‌کند. کاربر اجرایی فقط پروژه‌های واگذارشده را می‌بیند و فایل را دریافت می‌کند.
- فایل نام تصادفی دارد، اندازه و پسوند محدود است، MIME از امضای محتوا بررسی می‌شود و فایل خارج از static directory می‌ماند. مسیر دانلود از DB به مسیر امن محدود می‌شود. ZIP و سندهای Office هرگز extract یا اجرا نمی‌شوند.
- ورودی تلگرام و بله فقط در چت خصوصی پردازش می‌شود؛ پروژه یا متن محرمانه در گروه پاسخ داده نمی‌شود.
- لاگ‌ها متن پروژه، توکن‌های پیام‌رسان، رمز، کد دعوت یا بدنهٔ کامل update را ثبت نمی‌کنند. رویدادهای مدیریتی audit می‌شوند.

## کدها و توکن‌ها

روی سرور تنها از `/etc/projecthub/projecthub.env` با مجوز `0640 root:projecthub` استفاده کنید. کد فعال‌سازی مالک از `python -m app.cli issue-owner-code` می‌آید و ۲۴ ساعت و یک بار اعتبار دارد. دعوت تیم ۴۸ ساعت، و لینک اتصال پیام‌رسان یک ساعت اعتبار دارد. tokenهای خام فقط هنگام ساخت نشان داده می‌شوند؛ دیتابیس digest آن‌ها را نگه می‌دارد.

فایل ZIP قبلی شامل مقدارهای secret واقعی‌نما بود. مقادیر از گزارش، مستندات، نمونهٔ env و این repo حذف شده‌اند؛ اما حذف از نسخهٔ zip، token قبلاً افشاشده را باطل نمی‌کند. token ربات بله و تلگرام و رمز پایگاه‌دادهٔ قدیمی را تعویض کنید و در GitHub اصلاً commit نکنید.

برای مخزن خصوصی، دسترسی pull سرور را با یک Deploy Key فقط‌خواندنی یا روش سازمانی مدیریت‌شده بدهید. token شخصی GitHub را در URL clone، shell history یا فایل سورس قرار ندهید.

## گفتگو و حذف

Transcript و فایل‌های پیوست به‌صورت دائمی در دیتابیس و دیسک VPS نگهداری می‌شوند؛ retention خودکار پیاده نشده چون سیاست شما نگه‌داری آرشیو را می‌خواهد. هر فایل تا ۲۰ مگابایت است و حجم فایل‌های هر گفتگو به‌طور پیش‌فرض ۵۰۰ مگابایت سقف دارد؛ پس از پرشدن سقف، متن و مشخصات پیام آرشیو می‌شود اما بایت‌های فایل ذخیره نمی‌شوند. دکمهٔ پاک‌سازی مشتری همهٔ شناسه‌های پیام ثبت‌شده را برای حذف از نمایش سمت پیام‌رسان صف می‌کند؛ محدودیت API ممکن است بخشی از پیام‌ها را باقی بگذارد. آرشیو مدیریتی تا اقدام صریح مالک باقی می‌ماند.

حذف آرشیو در پنل، پیام‌های transcript و فایل‌هایی را که به پروژه‌ای تعلق ندارند پاک می‌کند و یک رویداد حسابرسی باقی می‌گذارد. حذف transcript فایل پروژه را از بخش پروژه پاک نمی‌کند. حذف حساب مشتری و پاک‌سازی کامل سوابق پروژه/مالی در نسخهٔ فعلی workflow جداگانه‌ای نیست.

## فایل و پشتیبان

فایل‌ها در `/var/lib/projecthub/uploads` با مجوز محدود ذخیره می‌شوند. VPS باید دیسک رمزگذاری‌شده و دسترسی SSH محدود داشته باشد. backup حاوی متن گفتگو و فایل‌هاست؛ آن را با یک کلید عمومی `age` خارج از سرور رمز کنید:

```bash
sudo BACKUP_RECIPIENT='age1...' bash scripts/backup.sh
```

کلید خصوصی رمزگشایی را روی همان VPS نگه ندارید. backup را در محل جدا و محدود نگه دارید و بازیابی را در محیط آزمایشی انجام دهید.

## مواردی که زیرساخت باید فراهم کند

TLS معتبر، به‌روزرسانی سیستم‌عامل و PostgreSQL، فایروال فقط برای SSH/HTTPS، سیاست rotate secretها، پایش فضای دیسک، هشدار خطای سرویس‌ها، و آزمون دوره‌ای restore لازم‌اند. اسکن بدافزار فایل‌ها و object storage در نسخهٔ اولیه فعال نیست؛ اگر فایل‌های مشتریان در محیط پرریسک دریافت می‌شوند، قبل از انتشار عمومی باید لایهٔ اسکن اضافه شود.
