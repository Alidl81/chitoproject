# معماری ChitoProject

## اجزای اصلی

| جزء | وظیفه |
|---|---|
| `app/bot/transport.py` | ارتباط HTTP با Telegram و Bale؛ محدودیت timeout، پیام خطای کنترل‌شده و دانلود فایل جریانی |
| `app/bot/runtime.py` | long polling مستقل هر پیام‌رسان؛ ثبت update در دیتابیس پیش از جلو بردن offset؛ قفل زمان‌دار poller |
| `app/bot/flow.py` | منوی مشتری و همکار، فرم درخواست، پیگیری، پاک‌سازی نمای چت و ثبت transcript |
| `app/bot/worker.py` | مصرف صف ورودی، اجرای هم‌زمان محدود، صف خروجی، retry، محدودیت ارسال در هر گفتگو و قفل worker |
| `app/web/` | احراز هویت، نقش‌ها، داشبورد، مدیریت پروژه، گفتگو، تیم و audit |
| `app/models.py` | مدل‌های SQLAlchemy برای کاربران، پروژه‌ها، transcript، فایل، دعوت، نشست و صف‌ها |
| `alembic/` | migration پایگاه‌داده؛ migration اولیه برای دیتابیس خالی است |
| `deploy/systemd/` | سرویس جداگانهٔ وب، worker و دو poller |

## دریافت و پردازش رویداد

1. Poller از Telegram یا Bale رویداد می‌گیرد.
2. رویداد در `incoming_updates` با قید یکتای `(platform, update_id)` ثبت و commit می‌شود.
3. فقط پس از commit، offset برای درخواست بعدی جلو می‌رود. اگر دریافت و ذخیره‌سازی قطع شود، پیام‌رسان همان رویداد را دوباره می‌دهد و قید یکتا تکرار را حذف می‌کند.
4. Worker ردیف‌های آماده را با `FOR UPDATE SKIP LOCKED` می‌گیرد. در هر اجرا یک worker فعال است؛ پردازش بین چت‌های مختلف هم‌زمان و درون هر چت مرتب است.
5. پیام ورودی، وضعیت فرم، نسخهٔ پیام کنترلی و پیام خروجی در یک تراکنش دیتابیس ثبت می‌شوند. بدنهٔ خام update پس از پردازش پاک می‌شود؛ transcript استاندارد و فایل‌های آن باقی می‌مانند.
6. ارسال بیرونی از `outbox_messages` انجام می‌شود. موفقیت، خطا، retry و شناسهٔ پیام در دیتابیس ذخیره می‌شود.

### مرز تضمین ارسال

ثبت ورودی و تغییر وضعیت در دیتابیس idempotent است. در ارسال بیرونی، اگر پیام‌رسان پیام را پذیرفته باشد اما اتصال پیش از ثبت نتیجه در دیتابیس قطع شود، retry ممکن است پیام را دوباره بفرستد؛ Telegram و Bale برای ارسال عمومی پیام کلید idempotency ارائه نمی‌کنند. برای کنترل اثر، پیام‌های UI با همان شناسهٔ کنترل ویرایش می‌شوند و worker ارسال‌ها را در هر چت مرتب می‌کند.

## مدل transcript

- هر گفتگوی خصوصی به `platform + chat_id` مقید است.
- منوی مشتری و مراحل ثبت با Inline Keyboard پیش می‌روند؛ کنترل اصلی در یک پیام کنترلی ویرایش می‌شود. ثبت پروژه پیش از گرفتن عنوان، فقط انتخاب «کامپیوتر» را نشان می‌دهد.
- پیام ورودی دارای شناسهٔ پیام پیام‌رسان است. پیام ویرایش‌شده نسخهٔ تازه می‌گیرد تا متن پیشین از بین نرود.
- متن هر ویرایش پیام کنترلی ربات جدا ثبت می‌شود، درحالی‌که روی صفحه معمولاً همان یک پیام Inline ویرایش می‌شود.
- callbackهای کاربر به‌صورت اقدام قابل‌خواندن ثبت می‌شوند؛ محتوای توکن دعوت وارد transcript نمی‌شود.
- پاسخ تیم پیش از ارسال در آرشیو ثبت و سپس در outbox ارسال می‌شود.
- تاریخچهٔ پشتیبانی با `support_session_id` در transcript برچسب می‌خورد. پاک‌سازی چت فقط شناسه‌های پیام نشست جاری را صف می‌کند؛ هیچ پیام آرشیوی حذف نمی‌شود. حذف transcript فقط از مسیر پنل مالک انجام می‌شود.
- فایل‌های پذیرفته‌شده در `conversation_files` و، در صورت ثبت پروژه، در `attachments` به همان کلید ذخیره‌سازی اشاره می‌کنند.

تلگرام برای دکمه‌های Inline سبک‌های مستند `primary`، `success` و `danger` را می‌پذیرد؛ پیاده‌سازی فقط همین مقادیر را برای اقدام اصلی، تأیید و لغو می‌فرستد ([Bot API](https://core.telegram.org/bots/api#inlinekeyboardbutton)). قالب مشترک برای بله این فیلد را حذف می‌کند و رنگ سفارشی یا گرادیانت را به بله نسبت نمی‌دهد.

## نقش‌ها و حدود دسترسی

`owner` همهٔ امکانات، دعوت نقش‌های مدیریتی، غیرفعال‌سازی اعضا و حذف transcript را دارد. `manager` پروژه‌ها، پاسخ به مشتری و دعوت نقش‌های محدودتر را مدیریت می‌کند. `reviewer` پروژه را بررسی می‌کند. `contributor` فقط پروژهٔ واگذارشده را می‌بیند. `support` گفتگوهای مشتری را می‌بیند و پاسخ می‌دهد. مجوزها در `app/permissions.py` متمرکزند و مسیرهای وب مستقل از نمایش منو آن‌ها را بررسی می‌کنند.

لینک دعوت تیم در وب token خام را در fragment مرورگر می‌گذارد؛ fragment به درخواست HTTP یا access log سرور فرستاده نمی‌شود. token فقط به‌صورت HMAC-SHA-256 digest و یک بار مصرف در دیتابیس نگهداری می‌شود. اتصال حساب پیام‌رسان نیز token جدا، نقش از پیش تعیین‌شده و انقضای کوتاه دارد.

## دیتابیس و هم‌زمانی

PostgreSQL محیط تولید است. SQLite فقط برای توسعهٔ تک‌پردازه‌ای به کار می‌رود. هر task هم‌زمان یک `AsyncSession` جدا می‌گیرد؛ pool هر پردازه محدود شده است. یک VPS اولیه چهار سرویس برنامه دارد: API، worker، Telegram poller و Bale poller.

برای شروع با دیتابیس خالی:

```bash
python -m app.cli migrate
```

برنامه startup schema را خودکار نمی‌سازد. هر تغییر آینده باید migration جدید داشته باشد؛ migration `0001_initial` پس از انتشار نباید ویرایش شود.
